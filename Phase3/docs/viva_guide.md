## 2. Core Concepts: Question & Answer Breakdown

### Q1: Where do the simulation inputs come from?
**Answer:**
All simulation inputs originate from native, validated SUMO XML files in the `sumo_files/` directory:
- `simulation.sumocfg`: The master configuration file specifying step size (1.0s), network file, and route file.
- `network.net.xml`: Compiled using SUMO's `netconvert` tool from `nodes.nod.xml` and `edges.edg.xml`. Defines the 4-arm junction `J0` (North, South, East, West approaches with 2 lanes each, 250m long).
- `vehicle_types.add.xml`: Specifies physical vehicle parameters (length, maximum speed, acceleration, deceleration, color) for `passenger`, `bus`, `delivery`, and `emergency` classes.
- `routes.rou.xml`: Generated deterministically by `simulation/traffic_generator.py` based on configurable traffic demand scenarios (Low, Medium, High).

### Q2: How does a vehicle enter SUMO?
**Answer:**
1. In `simulation/traffic_generator.py`, departure times are scheduled across the simulation duration using randomized intervals.
2. A departure entry is written to `routes.rou.xml`:
   ```xml
   <vehicle id="veh_medium_demand_001" type="passenger" route="route_N_S" depart="2.5" departLane="best" departSpeed="max"/>
   ```
3. At simulation time $t = 2.5\text{s}$, SUMO's car-following model (Krauss model) attempts to insert the vehicle onto the first lane of edge `N2J0`.
4. If the lane has sufficient safe distance (`minGap`), the vehicle enters the network and begins accelerating.

### Q3: How does Python communicate with SUMO through TraCI?
**Answer:**
- **TraCI (Traffic Control Interface)** is a client-server TCP socket protocol.
- `simulation/traci_client.py` launches SUMO as a subprocess with a communication port (`traci.start(...)`).
- In every time step, Python invokes `traci.simulationStep()`.
- Python then issues TraCI query commands:
  - `traci.vehicle.getIDList()`: Retrieves active vehicles on the road.
  - `traci.vehicle.getSpeed(v_id)`: Measures instantaneous velocity.
  - `traci.vehicle.getWaitingTime(v_id)`: Queries accumulated stopped delay.
  - `traci.trafficlight.setRedYellowGreenState(tl_id, state_str)`: Actuates signal heads.

### Q4: What counts as an "OS Scheduling Task" in this project?
**Answer:**
It is critical to distinguish between physical vehicles and software tasks:
- **Vehicles** are physical agents traveling on road edges inside SUMO.
- **OS Tasks** (`scheduler/task_model.py`) are user-space software processes generated by the traffic management application to process monitoring events:
  - `T1` (*Collect Telemetry*): Polling TraCI for vehicle coordinates.
  - `T2` (*Evaluate Signal Transition*): Computing phase timer expiration.
  - `T3` (*Persist Traffic Snapshot*): Writing telemetry records to MySQL.
  - `T4` (*Emergency Corridor Actuation*): Clearing intersections for priority ambulances.
  - `T5` (*Compute Approach Queue Density*): Analyzing stopped vehicles.
  - `T6` (*Aggregate System Summary*): Calculating throughput and travel time averages.

### Q5: How do FCFS, Priority, and Round Robin differ?
**Answer:**
- **FCFS (`scheduler/fcfs.py`)**:
  - Non-preemptive. Dispatches ready tasks strictly in arrival time order.
  - Suffer from the **Convoy Effect**: a long database write task (Burst=8) arriving early delays short critical tasks.
- **Priority Scheduling (`scheduler/priority.py`)**:
  - Convention: **Priority 1 = Highest Priority**.
  - Non-preemptive: Picks the highest-priority ready task when the CPU is free.
  - Preemptive: If a high-priority task arrives (e.g., Emergency Actuation, Priority 1), it immediately interrupts the currently running lower-priority task (e.g., Snapshot Persistence, Priority 4).
  - Yields the lowest average waiting time for critical tasks, but introduces more context switches.
- **Round Robin (`scheduler/round_robin.py`)**:
  - Preemptive. Enforces a time quantum $q$ (e.g., 2 ticks).
  - Every task receives equal time slices; uncompleted tasks rotate to the tail of the ready queue.
  - Eliminates starvation and guarantees bounded response time, but incurs context-switching overhead.

### Q6: How are Waiting Time and Turnaround Time calculated?
**Answer:**
Using foundational operating systems formulas:
$$\text{Turnaround Time} = T_{\text{completion}} - T_{\text{arrival}}$$
$$\text{Waiting Time} = \text{Turnaround Time} - \text{Burst Time}$$
$$\text{Average Waiting Time} = \frac{1}{N} \sum_{i=1}^N \text{Waiting Time}_i$$

### Q7: How does MySQL store and retrieve records?
**Answer:**
- `database/db_manager.py` manages a pooled connection to MySQL Server on port 3306.
- The schema contains 7 relational tables with primary keys, foreign keys (`ON DELETE CASCADE`), and indexes.
- `services/persistence_service.py` executes transactional inserts:
  - A `simulation_runs` row is inserted upon starting.
  - At every step, snapshots are batch-inserted into `traffic_snapshots`.
  - Upon completion, individual vehicle journeys are recorded in `vehicle_observations`.
  - When the scheduler runs, `scheduler_runs` and `scheduler_tasks` records are committed.
- All queries use parameterized SQL (`%s`) to guarantee injection immunity.
